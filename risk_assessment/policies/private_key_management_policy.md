## 1. Purpose and Scope

### 1.1 Purpose

This policy establishes the requirements for the secure generation, storage, distribution, rotation, revocation, and destruction of cryptographic private keys used by the **Secure Document Management & E-Signature System**. The goal is to protect the confidentiality and integrity of private keys to prevent unauthorised use, disclosure, or compromise.

### 1.2 Scope

This policy applies to:

- **Root CA private key** (`pki/root-ca/private/root-ca.key`)
- **Intermediate CA private key** (`pki/intermediate-ca/private/intermediate-ca.key`)
- **TLS server private key** (`pki/certs/server.key`)
- **User signing private keys** (`backend/keys/<user_id>_private.pem`)

This policy applies to all team members, system administrators, and any other parties with access to key material.

### 1.3 Policy Owner

**Policy Owner:** Security Administrator (users assigned the `admin` role within the system)

## 3. Key Generation

### 3.1 Algorithm and Key Size

- **Minimum key size:** RSA-2048 bits
- **Recommended key size:** RSA-4096 for CA keys; RSA-2048 for user signing keys
- **Hash algorithm:** SHA-256 (minimum); SHA-384 for CA certificates
- **Alternative:** ECDSA P-256 is an acceptable alternative for user signing keys

### 3.2 Generation Requirements

| Key Type | Generation Environment | Tool |
|---|---|---|
| Root CA key | Offline system (air-gapped), dedicated session | `openssl genrsa -aes256` |
| Intermediate CA key | Hardened server, restricted terminal session | `openssl genrsa -aes256` |
| TLS server key | Server; generated at deploy time | `openssl genrsa` or Let's Encrypt |
| User signing key | Backend server; generated by API (`generate_key_pair()`) | Python `cryptography` library |

### 3.3 Entropy Requirements

All key generation must use a cryptographically secure random number generator (CSPRNG). On Linux systems, `/dev/urandom` is used by OpenSSL and the Python `cryptography` library by default.

### 3.4 Passphrase Protection

CA private keys **must** be protected with a strong passphrase (minimum 20 characters, mix of character classes). User signing keys are stored without passphrase on the server but protected by filesystem permissions (see Section 4).

## 4. Key Storage

### 4.1 Root CA Private Key

| Requirement | Detail |
|---|---|
| **Location** | Offline storage only (USB hardware key or encrypted USB drive) |
| **Physical Security** | Locked cabinet or safe; access log maintained |
| **Online Presence** | NEVER stored on a network-connected system |
| **Copies** | Maximum two copies (primary + backup), both offline |
| **Backup copy location** | Separate physical location from primary |
| **Passphrase** | Required; stored separately from the key (password manager, not on USB) |

### 4.2 Intermediate CA Private Key

| Requirement | Detail |
|---|---|
| **Location** | Server filesystem: `pki/intermediate-ca/private/intermediate-ca.key` |
| **Permissions** | `chmod 600` (owner read/write only) |
| **Owner** | `appuser` (non-root Docker user) |
| **Passphrase** | Required; passphrase stored in environment variable `INTERMEDIATE_CA_PASS`, not in code |
| **Gitignore** | Directory `pki/intermediate-ca/private/` is in `.gitignore` — NEVER committed |

### 4.3 TLS Server Private Key

| Requirement | Detail |
|---|---|
| **Location** | `pki/certs/server.key` |
| **Permissions** | `chmod 600` |
| **Gitignore** | `*.key` is in `.gitignore` |
| **Rotation** | Rotate 30 days before TLS certificate expiry |

### 4.4 User Signing Private Keys

| Requirement | Detail |
|---|---|
| **Location** | `backend/keys/<user_id>_private.pem` |
| **Permissions** | `chmod 600` on each file |
| **Owner** | `appuser` (backend container user) |
| **Gitignore** | `backend/keys/` is in `.gitignore` — NEVER committed |
| **Access** | Never returned via API; used only server-side for signing operations |
| **Naming** | `<uuid4>_private.pem` and `<uuid4>_public.pem` |

## 5. Access Control

### 5.1 Principle of Least Privilege

Access to key material is restricted to the minimum necessary:

- **Only the `admin` role** may trigger user key generation (via `POST /api/admin/users/<id>/generate-key`)
- **Signing operations** are performed server-side by the backend API; the private key PEM bytes are never transmitted to the client
- **No direct file access** to `backend/keys/` or `pki/*/private/` from application code (only the crypto module reads these files)
- **Docker bind mounts** expose only `backend/keys/` and `pki/` to the backend container; the frontend container has no access

### 5.2 API-Level Enforcement

```
Document signing flow:
  Client → POST /api/documents/<id>/sign (JWT auth required)
         → Backend reads private key from filesystem (server-side only)
         → Computes RSA signature
         → Stores signature in DB
         → Returns success (never returns key material)
```

### 5.3 Audit Logging

Every key operation is logged to the `AuditLog` table with:
- `user_id` — who triggered the operation
- `action` — `KEY_GENERATED`, `DOCUMENT_SIGNED`, `KEY_REVOKED`
- `ip_address` — source IP
- `timestamp` — UTC timestamp
- `details` — JSON with key ID and certificate subject

## 6. Key Rotation

| Key Type | Rotation Frequency | Trigger |
|---|---|---|
| Root CA certificate | 10-year validity (replace at expiry) | Expiry or compromise |
| Intermediate CA certificate | 5-year validity (replace at expiry) | Expiry or compromise |
| TLS server certificate | Renewed 30 days before expiry (automated) | Expiry |
| User signing key | **Annually** | Annual cycle, role change, or compromise |
| User signing key (compromise) | **Immediately** | Suspected or confirmed compromise |

### 6.1 User Key Rotation Procedure

1. Admin triggers key rotation via `PUT /api/admin/users/<id>/rotate-key`
2. Backend generates new RSA-2048 key pair
3. Old key pair is securely deleted (overwritten with zeros, then deleted)
4. New public key is submitted for a new certificate from the Intermediate CA
5. User is notified; existing signatures (using old key) remain valid (verified against old public cert)
6. Operation logged in AuditLog

## 7. Certificate Revocation

### 7.1 Revocation Process

If a certificate must be revoked (key compromise, role change, user departure):

```bash
# Step 1: Identify the certificate serial number
openssl x509 -in pki/certs/<user_id>_cert.pem -noout -serial

# Step 2: Revoke via script
bash scripts/revoke_cert.sh <certificate_file>

# Step 3: Regenerate CRL
openssl ca -config pki/intermediate-ca/openssl.cnf -gencrl -out pki/intermediate-ca/crl.pem

# Step 4: Distribute updated CRL (copy to nginx certs location)
cp pki/intermediate-ca/crl.pem pki/certs/intermediate-ca.crl
```

### 7.2 CRL Update Timeline

- CRL must be updated **within 24 hours** of revocation
- CRL validity period: 30 days (nginx and backend check CRL on each signing operation)

### 7.3 Emergency Revocation

In the event of a suspected Root CA key compromise:

1. Take the system offline immediately
2. Notify all stakeholders
3. Generate a new Root CA key pair (offline)
4. Reissue all intermediate CA and user certificates
5. Conduct post-incident review

---

## 8. Key Destruction

When a key is no longer needed (rotation, user removal):

1. Overwrite the key file with zeros: `shred -u -z backend/keys/<user_id>_private.pem`
2. Confirm the file is removed
3. Log the destruction event in AuditLog (`action: KEY_DESTROYED`)
4. Revoke the corresponding certificate (see Section 7)

## 9. Incident Response

### 9.1 Indicators of Compromise

- Unexpected files in `backend/keys/` or `pki/*/private/`
- AuditLog entries showing key access outside normal hours or from unexpected IPs
- Reports of forged signatures passing verification
- Unauthorised `git add` of private key files (blocked by `.gitignore`, but check `git status`)

### 9.2 Response Steps

| Step | Action | Responsible |
|---|---|---|
| 1 | **Contain** — Isolate affected service(s), revoke compromised key immediately | Security Admin |
| 2 | **Assess** — Determine scope: which keys, which documents affected | Security Admin + Team |
| 3 | **Notify** — Inform project supervisor and affected users | Mohsin Zia |
| 4 | **Recover** — Generate new key pair, reissue certificates, re-sign affected documents | Backend Lead |
| 5 | **Review** — Document incident, update this policy if necessary | All |
